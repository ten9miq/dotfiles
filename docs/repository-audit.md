# リポジトリ構成・設定監査

調査日: 2026-07-11

## 結論

このリポジトリは、Bashを中心に各種dotfilesを `$HOME` へ配布する基本構成としては成立している。Bash系スクリプト31件はすべて構文検査を通過し、秘密鍵やAPIトークンそのものも追跡ファイルからは検出されなかった。

一方、実行時の安全性と移植性には改善が必要である。特に、ログイン時の自動更新がローカル変更を破棄し得ること、セットアップ内の子処理失敗が全体成功として表示されること、SSHの安全性を全接続で弱める設定は優先して修正すべきである。

## 調査範囲

- 追跡対象ファイルの構成と責務
- `setup.sh`、`setup_env.sh`、各ディレクトリの`init.sh`
- Bash、Zsh、Fish、Vim、tmux、Git、SSH設定
- 外部ダウンロードと自動更新処理
- 秘密情報・個人情報らしき文字列
- Bash構文検査と主要な制御処理の再現テスト

## 検証結果

| 検証 | 結果 |
|---|---|
| Bash系スクリプト31件の `bash -n` | 全件成功 |
| `git diff --check` | 問題なし |
| APIキー、トークン、秘密鍵本文 | 検出なし |
| `setup.sh` のバックグラウンド失敗と`wait` | 子処理失敗後も`wait`が0となることを再現 |
| `is_wsl` | `os_type=wsl`で終了ステータス1となることを再現 |
| SSH秘密鍵探索式 | `id_rsa`だけを検出し、単独の`.pem`と`.ppk`を検出しないことを再現 |
| Zsh/Fish固有構文 | 現在のWindows環境に実行環境がなく未検証 |
| 実ホームへの`setup.sh`適用 | 既存設定を変更するため未実施 |

## 重大度: 高

### 1. ログイン時の自動更新による作業中変更の破棄は対策済み

対象: `shell_common/check_update.bash`

Linuxで `$HOME/dotfiles` にリモート更新があると、ログイン処理中に次を実行する。

```bash
git reset --hard $(git log --pretty=format:%H | head -1)
git pull origin ${branch_name}
./setup.sh
```

`git reset --hard` の対象は現在のHEADと同じだが、追跡ファイルの未コミット変更を消去する。ユーザーの明示操作なしにログイン時に実行されるため、データ消失リスクが高かった。

2026-07-11に、リポジトリへ移動した直後に `git status --porcelain` を確認する処理を追加した。出力が空でない場合は、fetch、reset、pull、setupを実行せず、元のディレクトリへ戻って自動更新を正常終了する。状態確認自体に失敗した場合も更新せず、エラーを返す。

これにより、追跡済み変更、ステージ済み変更、未追跡ファイルがある通常のdirty worktreeは保護される。ただし、無視ファイルは`git status --porcelain`に現れず、`reset --hard`自体も残っているため、将来的には自動更新を通知のみへ変更するのがより安全である。

推奨対応:

1. 自動更新を通知だけに変更する。
2. fast-forward可能か確認し、`git pull --ff-only`を使用する。
3. `reset --hard`を削除する。
4. 更新と`setup.sh`実行は明示コマンドに分離する。

### 2. セットアップの一部が失敗しても成功表示になる

対象: `setup.sh`

各スクリプトはバックグラウンド実行され、最後に引数なしの`wait`を呼ぶ。再現テストではバックグラウンド処理が失敗しても最終`wait`は0となり、スクリプトは常に`COMPLITE.`を表示して終了する。

これにより、Git設定だけ失敗した、gomi取得だけ失敗した、SSH設定だけ失敗した、といった部分適用を利用者が成功と誤認する。

推奨対応:

- 各PIDを配列へ保存し、個別に`wait "$pid"`して失敗数を集計する。
- 1件でも失敗した場合は終了ステータスを非0にし、失敗したスクリプト名を最後に一覧表示する。
- 完了表示を`COMPLETE`へ修正する。

### 3. SSHの弱い設定が全接続へ適用される

対象: `ssh/config`

```sshconfig
ForwardAgent yes
HostKeyAlgorithms +ssh-dss
```

`ForwardAgent yes`がグローバルに設定されているため、接続先ホストが侵害された場合に転送中のエージェントが悪用される範囲が広い。`ssh-dss`も古く弱いアルゴリズムであり、全接続へ追加する必要はない。

推奨対応:

- デフォルトを`ForwardAgent no`にし、本当に必要な信頼済みHostだけ`yes`にする。
- `HostKeyAlgorithms +ssh-dss`を全体設定から削除し、どうしても必要な旧機器だけHostブロックへ限定する。
- `PermitLocalCommand`とControlMasterも必要なHost範囲へ限定することを検討する。

### 4. WSL判定関数がCygwinを判定している

対象: `setup_env.sh`

```bash
is_wsl() {
  [[ `os_type` == "cygwin" ]]
}
```

`os_type`はWSLで`wsl`を返すため、`is_wsl`はWSLで偽、Cygwinで真になる。現在のコードでは直接 `os_type` を比較する箇所も多いが、共通関数を今後利用すると誤分岐する。

推奨対応: 比較対象を`wsl`へ修正し、OS判定関数ごとのテーブル駆動テストを追加する。

### 5. SSH鍵探索式が`.pem`と`.ppk`を正しく検出しない

対象: `shell_common/startup.bash`

現在のfind式は`-or`と暗黙のANDの優先順位により、実質的に`id_rsa*`または「`.ppk`かつ`.pem`」を探す。再現テストでは`id_rsa`だけが見つかり、単独の`key.pem`と`key.ppk`は見つからなかった。

また、文字列を`eval`し、結果を空白区切りの`for`で処理するため、鍵のパスに空白があると壊れる。

推奨対応:

- find条件を括弧でグループ化する。
- `eval`を削除する。
- `-print0`とnull区切りの読み込みを使う。
- 秘密鍵候補を自動で全追加する設計自体も見直し、明示リストを検討する。

## 重大度: 中

### 6. Git認証情報を平文保存する設定がWSLで生成される

対象: `git/init.sh`

WSLでは新規`~/.gitconfig.local`へ`credential.helper = store`を書き込む。Gitの資格情報がホームディレクトリへ平文保存される。コメントには注意書きがあるが、セットアップが自動選択するため安全なデフォルトではない。

推奨対応: Git Credential Manager、OSの資格情報ストア、短時間の`cache`を優先し、`store`は利用者が明示選択した場合だけにする。

### 7. Gitユーザー情報が個人値で固定されている

対象: `git/init.sh`

初回生成される`.gitconfig.local`に氏名とメールアドレスがハードコードされている。個人専用リポジトリなら動作上は問題ないが、公開・再利用・別アカウント利用時に誤った著者情報を付ける。

推奨対応: 環境変数、対話入力、追跡されないサンプルファイルのいずれかへ分離する。

### 8. gomiは未固定のlatestバイナリを検証せず実行する

対象: `bin/init.sh`

GitHub Releasesの`latest`を毎回ダウンロードし、チェックサムや署名を検証せず実行する。上流更新直後の不具合とサプライチェーン侵害が、次回セットアップへ即時反映される。

推奨対応:

- 安定性を優先する場合はバージョンとSHA-256を固定する。
- latestを維持する場合も、上流がチェックサムを提供した時点で検証を追加する。
- curlからtarへのパイプでは`pipefail`を局所的に有効化するか、アーカイブを一度保存して双方の終了状態を確認する。

### 9. Zi、dein、fzfも上流の先端へ依存する

対象: `zsh/.zshrc`、`vim/.vimrc`、`bin/init.sh`

Ziとfzfはshallow clone、deinは初回cloneと自動プラグイン導入を行い、基本的にリビジョンを固定していない。環境を再構築する時期によって結果が変わる。

推奨対応: 管理ツール本体だけでもタグ・コミットを固定し、更新用コマンドと通常セットアップを分ける。プラグイン一覧には更新確認日を残す。

### 10. macOS対応を掲げる一方、バックアップ処理がGNU cp依存

対象: `setup_env.sh`

バックアップで`cp -b --suffix=...`を使うが、macOS標準のBSD cpはGNU形式の`--suffix`をサポートしない。`os_type`はmacOSを正式分岐として扱うため、宣言上の対応範囲と実装が一致していない。

推奨対応: `cp`のバックアップオプションへ依存せず、既存ファイルを日時付きパスへ明示的にコピーしてから新ファイルを配置する。

### 11. パスの引用不足により空白を含むホーム・リポジトリで壊れる

対象: `setup_env.sh`と各`init.sh`の多数箇所

`$PROJECT_PATH`、`$THIS_SCRIPT_PATH`、find結果、コピー先などが引用されていない箇所が多い。Windowsユーザー名や配置パスに空白があると単語分割・グロブ展開が発生する。

推奨対応: 新規コードだけでなく配布経路を優先し、`"$var"`、配列、`find -print0`へ段階的に変更する。

### 12. エラートラップが非対話環境で停止する

対象: `error_trap.sh`

エラー時に必ず`read -p " Enter to close:"`を実行する。CI、SSHの非対話コマンド、標準入力がない自動化では停止または意図しない入力消費が起きる。

推奨対応: `[[ -t 0 ]]`のときだけ待機し、それ以外はエラー情報を出して元のステータスで終了する。

### 13. `setup.sh`はリポジトリ外から実行できない

対象: `setup.sh`

冒頭で`source ./setup_env.sh`としているため、カレントディレクトリがリポジトリルートであることを暗黙に要求する。他の`init.sh`は自身の位置を基準にしており、設計が一貫しない。

推奨対応: `BASH_SOURCE`からルートを解決し、絶対パスで`setup_env.sh`を読み込む。

### 14. ZshでBash向けkubectl補完を読み込む

対象: `zsh/.zshrc`

```zsh
source <(kubectl completion bash)
```

Zshでは`kubectl completion zsh`を利用すべきである。Bash向け補完は関数・補完登録方式が異なり、環境によってエラーまたは補完不全になる。

### 15. WSL/rootでcompinitのセキュリティ確認を省略する

対象: `zsh/.zshrc`

速度対策としてWSLまたはrootで`compinit -C`を使う。キャッシュを再利用する一方、補完ディレクトリの安全性再検査を省略するため、特にrootシェルでの利用は慎重に扱う必要がある。

推奨対応: rootでは信頼済み所有者・権限を確認した固定`fpath`だけを利用し、単純な速度理由で検査を省略しない。

### 16. SSH用と書かれたtmux自動起動がローカルでも発動する

対象: `shell_common/startup.bash`

コメントは「SSHログイン時」だが、条件はtmuxの存在と`$TMUX`が空であることだけで、`$SSH_CONNECTION`を確認していない。ローカルログインシェルでもtmuxへattachまたは新規作成する。

さらに`if ! $(tmux attach)`はコマンド置換を不要に挟んでいる。`if ! tmux attach`とする方が終了状態と端末入出力を明確に扱える。

## 重大度: 低

### 17. FishのPATHを`/bin`から作り直す

対象: `fish/fish/env.fish`

`set -gx PATH /bin`で継承PATHを破棄してから既知ディレクトリを追加する。再現性は高いが、Homebrew、言語ランタイム、企業環境固有のPATHを消す可能性がある。

### 18. fish_variablesをリポジトリで直接配布する

対象: `fish/fish/fish_variables`

現状は色やキーバインド等だけで秘密情報はない。ただしFishのuniversal variablesはツール操作により環境固有値が追加され得るため、将来の意図しないコミットに注意が必要である。必要な設定を`config.fish`へ明示する方式の方がレビューしやすい。

### 19. バックアップ保存先が平坦で保持期限がない

対象: `setup_env.sh`

バックアップをすべて`$HOME/.bak_dotfiles/`直下へ移動する。異なる元パスに同名ファイルがある場合の識別が弱く、秒単位タイムスタンプの衝突余地がある。削除・保持期限もない。

### 20. README、対応環境表、復旧手順、CIがない

ルートにREADMEや自動テスト設定がなく、必要コマンド、対応OS・シェル、実行方法、バックアップからの復旧方法が利用者向けにまとまっていない。AI向けガイドはあるが、利用者向けの入口にはならない。

推奨対応:

- READMEに対象OS、前提コマンド、実行方法、変更されるパスを記載する。
- 最低限`bash -n`とShellCheckをCIで実行する。
- Zsh、Fish、TOMLの構文検査も対応ランタイムで追加する。
- 一時HOMEを使った配置テストを用意する。

## 良好な点

- 秘密鍵、APIキー、アクセストークン本文は追跡されていない。
- Gitの個人設定を`.gitconfig.local`へ分離する構造自体は適切である。
- SSH設定ファイルの配置後にディレクトリ700、config 600を設定している。
- 多くの配置処理で既存ファイルとの差分確認とバックアップを意図している。
- gomiの置換は一時ファイルを経由し、ダウンロード・展開成功前に既存バイナリを消さない。
- `AGENTS.md`と調査ドキュメントに、実ホームを直接使わない検証方針が明記されている。
- VimとZshのプラグイン構成が文書化され、不要依存の削除が進んでいる。

## 推奨する修正順序

1. `check_update.bash`から自動`reset --hard`と自動適用を除去する。
2. `setup.sh`で子処理の失敗を集計し、正しい終了ステータスを返す。
3. SSHの`ForwardAgent`と`ssh-dss`をHost単位へ限定する。
4. `is_wsl`とSSH鍵探索式を修正する。
5. WSLの平文Git credential helperを安全な方式へ変更する。
6. `setup.sh`の実行位置依存とパスの引用不足を修正する。
7. 外部依存を固定・検証し、更新と通常セットアップを分離する。
8. Zshのkubectl補完、compinit、tmux起動条件を修正する。
9. 一時HOMEの統合テストとCIを追加する。
10. READMEと復旧手順を整備する。

## 修正時の検証方針

- 実ホームではなく一時`HOME`を使用する。
- Linux、WSL、macOS相当のOS判定を関数単位でテストする。
- 各`init.sh`の成功・失敗を意図的に作り、`setup.sh`の終了状態を確認する。
- パスに空白、日本語、ワイルドカード文字を含むケースを用意する。
- SSH・Gitの生成設定に弱いデフォルトや個人値が含まれないことを検査する。
- 外部ネットワーク失敗時にも既存設定が破損しないことを確認する。
